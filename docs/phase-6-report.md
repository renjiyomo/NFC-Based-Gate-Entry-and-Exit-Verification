Issuance now checks the destination coin first. Known active/pending references are blocked and their owner shown to the authorized administrator; unknown/unrelated data is also blocked. Empty or retired/expired references can be used. Explicit retirement is required before live-coin reuse. At write time, the reader scans again and checks content plus available transient serial before calling native write. Another coin or changed contents stop the operation. This reduces accidental overwrites in the application; it is not physical attestation, persistent UID binding or protection from external writes/cloning. The read-before-write pattern is supported by the [Web NFC specification](https://w3c-cg.github.io/web-nfc/).

A separate frontend issue found during investigation was that an earlier saved match could leave activation available after a later failed read-back or another write. Local readiness now resets for every write/read attempt and requires a fresh matching read plus successful backend acknowledgement. The HTTP regression separately verifies that another person's valid reference cannot complete the pending issuance. This fix does not reinterpret the user's overwrite as a wrong-reference acceptance.

## Implemented

- Shared `NdefAdapter` starts native NFC directly from the user's button gesture. It allows one radio operation at a time, attaches read listeners before scan, stops after the first result and releases listeners/signals on success, error, cancellation or a 30-second timeout. Timeout/cancel also settle if the native promise fails to respond to abort.
- Capability detection distinguishes secure context, direct browser tab, API presence and page visibility. Native errors use fixed redacted messages for permission denial, unavailable radio, incompatible tag/device, read/write failure, malformed record, timeout and cancellation. Native error text and tag data never appear in diagnostics.
- Authenticated **NFC setup** is available to administrators and guards. Permission state queries do not prompt automatically. **Check NFC access** starts/stops the radio; **Read reference format** discards its result without backend submission, registration claim or passage creation. Backgrounding/unmount cancels operations; a new button tap is required to restart.
- Real issuance and guard scanner share capability guidance and explicit radio cancellation controls. Writing, separate matching read-back, activation, backend verification, identity review and observed-passage confirmation remain distinct. References stay in transient memory; backend stores digests. Existing network uncertainty/recovery and server idempotency rules remain active.
- Destination checks are administrator-only and source-isolated. They write only a redacted audit reason/source, never raw references or serials. Native write starts from a reading event after the destination comparison; cancellation/timeouts still release the radio. Matching read-back readiness is invalidated by stale/failed/cancelled operations and cannot be restored by an older asynchronous completion.
- Permissions Policy explicitly permits NFC for the same origin; camera, microphone and geolocation remain denied. Existing no-store, no-referrer and framing protections apply.
- Separate `nfcheck_hardware` workspace on loopback port 8003 uses a distinct runtime account, application key, encrypted session cookie and private account handoff. It has two synthetic people, a test gate and separate admin/two guard accounts. Startup creates no credentials or passages, preserves existing lab records and does not reset schemas or main passwords. Simulator routes reject this schema. Hardware workspace requests require local/testing mode, explicit flag and loopback client.
- `scripts/connect-phone.ps1 Status|Connect|Disconnect` uses the existing Google-signed Android SDK ADB, checks the server/process and one authorized USB device, forwards only port 8003, refuses conflicting/unowned mappings and disconnects only the mapping it owns. It does not enable wireless debugging, expose a LAN listener, operate the phone UI, restart servers or install software. The ignored receipt contains a device hash, not its serial.

1. Keep the vivo unlocked and connected by a data cable. Enable Developer options → USB debugging. Approve **Allow USB debugging?** for this laptop. File Transfer alone is insufficient. If ADB reports unauthorized, reconnect while unlocked and approve the RSA fingerprint prompt. Do not bypass browser security warnings or install unknown certificates.
2. On the laptop, run `scripts/dev.ps1 hardware`, then `scripts/connect-phone.ps1 Connect`. A successful result identifies the model/Android release and confirms forwarding. If unauthorized/no device, stop here and resolve the phone prompt. Do not expose the app to Wi-Fi as a shortcut.
3. Open **http://localhost:8003/login** in **Chrome on the phone**. Use the private `admin` entry in `.tools/secrets/hardware-accounts.json`, then open **NFC setup**. Search the phone's Settings for NFC and turn it on; menu names vary by manufacturer. Record actual model, Android/Chrome versions and app commit in acceptance notes. Repeat access checks when changing devices.
4. Tap **Check NFC access** and allow Chrome's NFC prompt. Report the exact redacted result. An API-detected result or successful access probe is not tag acceptance.
5. Use only the four repurposed coins. Preserve active employee HW-TAG-08 and the six old-system coins. Reload the registry to load the new assets. First check HW-TAG-08 through **Issue credential → Check NFC coin**; expect Employee One and **Coin not ready for overwrite**, with no mutation. Then check a DIFFERENT blank or already-retired test coin. For student restoration choose HW-STUDENT-01, fresh label **HW-STUDENT-NEW-01**, and prepare. Tap **Write checked NFC coin** with only that checked destination present. Remove it, tap **Read back NFC tag**, and present the same coin separately. Activate only after the match. Keep Chrome visible and finish within ten minutes. Lost receipt requires cancellation/new label. A controlled test can deliberately present the unchanged active employee coin at write/read-back: the write must stop before overwrite and mismatched read-back must keep activation disabled. Do not erase/revoke the active employee coin for this test. Unknown/protected contents require separate read-only inspection, not guessing passwords or permanent locking.
6. Sign out and sign in on the phone using the separate `guard1` entry. Select `HW-GATE-01`, choose Entry, scan the tag, compare the synthetic identity and explicitly confirm the lab passage using the campus-document fallback. No photograph is fabricated. Scan alone must create no passage. Repeat with Exit; use the same physical tag across roles without copying its reference.
7. Work through the remaining physical matrix below. Record which steps were actually observed versus reported by the tester. Keep references, nonces, passwords and personal photos out of notes/screenshots. Leave test tags writable. Use only the isolated hardware workspace.
8. After testing, run `scripts/connect-phone.ps1 Disconnect`; disconnect the cable and turn off USB debugging when it is no longer needed. The helper leaves unrelated mappings/server processes alone.

Chrome supports Web NFC in a top-level secure context with a user gesture and permission; screen lock/page visibility affect operation. USB forwarding maps a phone-local address to the laptop service without LAN exposure, and loopback HTTP is potentially trustworthy. Ordinary LAN HTTP is insufficient. [Chrome Web NFC](https://developer.chrome.com/docs/capabilities/nfc), [Chrome USB port forwarding](https://developer.chrome.com/docs/devtools/remote-debugging/local-server), [MDN secure contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts).

NFC Tools' Read tab reports tag details and writable/locked status. NXP distinguishes permanent memory locks from password-protected access. [NFC Tools documentation](https://www.wakdev.com/en/apps/nfc-tools-android.html), [NXP NTAG21x write protection](https://docs.nxp.com/bundle/NTAG213_215_216/page/topics/write.html).

## Limits and next step

The user-reported probes establish one successful NFC start on each phone setup. First vivo write/read-back/activation, staged guard Entry/Exit and blank-coin rejection have the evidence described above; expired and cancelled reviews have no linked passage. RF range, antenna placement, tag capacity/formatting/lock state, permission-denial and radio interruption behavior, repeated-write reliability, broad device/browser compatibility and institutional identity/passage validation are not established. Web NFC supplies NDEF data, not cryptographic identity or anti-cloning protection. A mock read-back is never hardware evidence. Development defaults remain 30-second review and 10-second duplicate window pending campus validation.
