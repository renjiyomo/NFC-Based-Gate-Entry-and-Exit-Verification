# Deployment preparation

Phase 11 prepares a reviewable release procedure; it does not deploy this workstation or authorize live campus operation. Current main/simulator/hardware services remain loopback-only. The shared XAMPP Apache project URL must continue returning 403.

## Candidate configuration and boundaries

[Production environment template](../deploy/production.env.example) and [Nginx/PHP-FPM illustration](../deploy/nginx.conf.example) are unapplied examples. The Nginx file has not been syntax-tested on this Windows laptop. Domain, host OS, certificate, FPM socket, database location, SMTP and operating owners still need approval. No hosting/payment account, firewall rule, DNS record, certificate or shared service was changed.

Use a supported, patched PHP runtime compatible with composer.lock and the required extensions, the pinned application dependencies, Oracle MySQL 8.4 compatibility, built Vite assets and a dedicated web runtime. The verified local baseline is PHP 8.5.12/MySQL 8.4.13; recheck patch advisories before a future release. Node is a build dependency, not an additional gate application server. The production document root must be the release's **public** directory. Never serve the repository root, .tools, .env, private storage or source through Apache aliases. Do not use artisan serve or the PHP built-in router for operations.

The application currently limits migrations to its four recognized local schemas, exact MySQL version and project data directory. **A different production instance is deliberately not a valid migration target yet.** Once the actual host is chosen, review and test a narrow target-identity allowlist and migration credential there. Never remove the guard or run local provisioning scripts against an institutional/shared database. Runtime credentials must remain separate from schema maintenance credentials, with the same per-table/column restrictions documented in [database setup](database-setup.md).

## HTTPS and phone access

Use a stable institution-approved HTTPS origin with a certificate trusted by every guard phone. Validate the complete chain, renewal/expiry monitoring, phone clock, Chrome secure-context status, NFC permission and actual tag read/write. Self-signed warning bypasses and browser insecure-origin flags are not an operational setup. Port 8003 plus authorized USB reverse is a local laboratory workflow only.

Terminate TLS directly at the dedicated app server where possible. If a reverse proxy is required, explicitly trust only its addresses/forwarded headers, reject arbitrary Host values and verify generated reset links, redirects, Secure cookies and client attribution through it. Do not trust every proxy. The template assumes direct TLS termination and an approved fixed server_name. Validate HTTP-to-HTTPS redirects, CSP, no-store responses and short initial HSTS before increasing duration. HTTP/HTTPS, proxy behavior and Nginx syntax are not certified by the local preflight command.

## Release and migration procedure

1. Record approved host, domain, release commit, runtime versions, database identity, operators, privacy authorization and maintenance/manual-outage window. Keep application/DB writes quiet for the cutover. Take a verified backup and keep the prior release plus its compatible schema plan.
2. Build an isolated release from a reviewed commit and lockfiles. In CI/staging, run the full `scripts/dev.ps1 check` equivalent. Install PHP production dependencies using `composer install --no-dev --optimize-autoloader`; build frontend with `npm ci` and `npm run build`. Do not run dependency update commands during deployment. Re-test the production dependency set on the chosen host.
3. Supply a protected environment outside public access. For an existing database, retain its correct APP_KEY; **do not run key:generate as an update/restore step**. Configure the runtime DB user, HTTPS origin, encrypted database sessions/Secure/HttpOnly/SameSite cookies, private local storage and approved TLS SMTP. Main/production AI is disabled. Exclude .tools, private AI/account files, lab environments, dumps, development credentials, node_modules, Git metadata and research screenshots from the serving release.
4. Apply only reviewed additive migrations with the approved maintenance identity after target validation. On the current local instance the supported command remains `scripts/dev.ps1 migrate`; it visits the four fixed schemas and reapplies narrow runtime grants. No new migrations are needed for Phase 11. Do not use migrate:fresh, reset or automatic down-migration rollback.
5. Make only storage and bootstrap/cache writable by the service identity. Keep private photos on protected persistent storage outside public access. Preserve that storage and the environment/key across release switches. No public storage symlink is needed. Configure private rotated logs and backups under an approved retention policy.
6. After final environment values are supplied, use Laravel configuration/route/view caches in the separate release and run `php artisan nfcheck:check-deployment --json`. A nonzero result requires review. The command performs no database/network writes and reveals only check booleans. Its success is configuration evidence only; it does not approve mail, TLS, DB grants, recovery, research or operations.
7. Validate sign-in/reset/logout, role/object denials, assigned guards, private photos and downloads, main AI exclusion, a separate synthetic staging tag flow, record reconciliation and a clean error path. `/up` confirms framework boot, not database/mail/NFC health. Run dependency and TLS/host checks on the real target. Switch traffic only after the accountable institution/operator accepts the evidence.
8. Reload only deployment-owned PHP workers after a future release, with a defined rollback window. This phase has not restarted any current service. For rollback, prefer the prior compatible release with the retained database; restore a database only under the controlled recovery procedure. Reconcile any writes after the backup before reopening.

No production scheduler has been installed. Review/credential expiry is enforced during operations; the existing expire-review/expire-credential commands are housekeeping and require an intentional host-specific schedule if later desired. Anomaly detection remains manual. Production AI generation and summary workers are excluded; local synthetic workers remain unchanged.
